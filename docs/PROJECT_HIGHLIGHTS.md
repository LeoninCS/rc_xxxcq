# 项目亮点与技术选型

## 架构选型

```
业务系统 → 通知 API → 消息队列 → Workers → 外部 API
```

题目要求做一个内部的 HTTP 通知投递服务，让业务系统把对外通知交给它，由它负责后续发送和失败处理。很容易想出生产者-消费者模型，即外部服务消费业务系统发送的请求。

其实可以很直觉性地想到使用消息队列。但还是介绍一下为什么要用消息队列。

- 对于高并发的请求，需要削峰和异步来缓解系统压力。
- 对于整个系统架构来说，采用消息队列可以降低系统耦合度，后续添加新的外部服务也更容易。
- 对于生产者-消费者模型，很容易想到要保证消息可靠传递，采用消息队列，可以复用消息持久化、消费确认等成熟机制，降低可靠消息传递的实现成本。
- 对于承担不同业务职责的消费者，应按业务划分独立队列，以隔离消息积压，并支持独立的重试策略和扩容。同一业务内的多个 Worker 实例可共享队列，实现任务的并行处理。
